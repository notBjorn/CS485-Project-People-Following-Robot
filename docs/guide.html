People-Following Robot

Everything for the CS485 project in one place: how to set up a machine, run the simulation, move the person around, fix what breaks, and how the pieces fit together.

Quick start

The machine is already set up and the repo is cloned? Pick a scenario. Every command runs from the repo folder, and each terminal is its own window or tab.

The person walks a loop on its own: the easiest setup for testing a follower.

Terminal 1 · simulation
./scripts/launch_sim.sh world:=person_world
Terminal 2 · person walks
./scripts/launch_human_waypoints.sh

Default route: a 6 m square around the robot at 0.3 m/s, looping. Change it in src/people_follower/config/human_waypoints.yaml, or with the waypoint planner below.

Terminal 1 · simulation
./scripts/launch_sim.sh world:=person_world
Terminal 2 · keep focused
./scripts/launch_human_teleop.sh

Keys: i forward · , back · j/l turn · k stop · q/z faster/slower. The person keeps moving until you press k.

Terminal 1 · simulation
./scripts/launch_sim.sh            # box_room
Terminal 2 · keep focused
./scripts/launch_teleop.sh

Same keys as above. Both robots take stamped velocity commands on /cmd_vel, and the script sets that up for you. Add robot:=turtlebot4 to the simulation command to drive the TurtleBot 4 instead of TIAGo.

Navigation needs a saved map. warehouse, maze and depot ship with one. box_room and person_world don't have one yet.

Make a map (guided)
./scripts/make_map.sh box_room
Navigate automatically
./scripts/nav_demo.sh world:=warehouse
!

On the WSL laptop the simulated lidar is broken on the GPU (see troubleshooting), so mapping and navigation only work there in slow software mode. Use the lab machine.

Check that everything is alive

With a simulation running, this reports sensor rates, whether the robot is localized, and which navigation nodes are up:

./scripts/check_sim.sh

To stop: press Ctrl+C in each terminal. If something is left behind, run ./scripts/kill_sim.sh.

Robots: TIAGo and TurtleBot 4

Every launch, demo and mapping script takes robot:=tiago (the default) or robot:=turtlebot4, e.g. ./scripts/demo_uwb_follow.sh robot:=turtlebot4. Both carry UWB anchors 1–4 and the rest of the project sees the same topics on both, so teleop, UWB following, auto-mapping and navigation don't change. launch_follow.sh, auto_map.sh and nav_automation_node check which robot is running and only undock the TurtleBot 4.

Where TIAGo comes from

PAL Robotics' own TIAGo simulation only supports ROS 2 Humble with Gazebo Classic. We use the Gazebo Harmonic port in the EasyNav playgrounds: easynav_playground_tiago_description (URDF, meshes, ros2_control controllers) and easynav_playground_tiago_worlds (its ROS ↔ Gazebo bridge config). EasyNav itself is not used; navigation is still Nav2.

tiago.launch.py spawns that robot, with UWB anchors added, into our worlds: it adds Gazebo's Sensors, Imu and ForceTorque systems to a temporary copy of the world when they are missing, starts every controller, reuses the EasyNav bridge config with /scan_raw renamed to /scan, and runs tiago_base_relay for /cmd_vel and /odom. Tune TIAGo's Nav2 or SLAM in src/people_follower/config/tiago/, then ./scripts/build.sh.

Machine setup

A one-time job per machine. You need Ubuntu 24.04 (Jazzy only supports 24.04) and sudo access.

  1. Add the official ROS 2 apt repository 
    sudo apt update && sudo apt install curl
export ROS_APT_SOURCE_VERSION=$(curl -s https://api.github.com/repos/ros-infrastructure/ros-apt-source/releases/latest | grep -F "tag_name" | awk -F\" '{print $4}')
curl -L -o /tmp/ros2-apt-source.deb "https://github.com/ros-infrastructure/ros-apt-source/releases/download/${ROS_APT_SOURCE_VERSION}/ros2-apt-source_${ROS_APT_SOURCE_VERSION}.$(. /etc/os-release && echo $VERSION_CODENAME)_all.deb"
sudo dpkg -i /tmp/ros2-apt-source.deb
sudo apt update && sudo apt upgrade
  2. Install ROS, Gazebo, TurtleBot 4 and Nav2 
    sudo apt install ros-jazzy-desktop ros-dev-tools ros-jazzy-ros-gz \
  ros-jazzy-turtlebot4-simulator ros-jazzy-turtlebot4-desktop \
  ros-jazzy-turtlebot4-navigation ros-jazzy-nav2-simple-commander
sudo rosdep init && rosdep update

    Gazebo Harmonic comes with ros-jazzy-ros-gz. Don't also add the OSRF Gazebo repository, because mixing the two causes conflicts.

  3. Check the GPU 
    sudo apt install mesa-utils && glxinfo -B | grep "renderer string"

    It should name the real GPU. If it says llvmpipe, the simulation will crawl. For NVIDIA: sudo ubuntu-drivers install, then reboot.

  4. Optional: load ROS in every new terminal 
    echo '[ -f /opt/ros/jazzy/setup.bash ] && source /opt/ros/jazzy/setup.bash' >> ~/.bashrc

    The repo scripts load ROS themselves; this is only for typing ros2/gz by hand.

  5. Get the code and build 
    git clone git@github.com:notBjorn/CS485-Project-People-Following-Robot.git
cd CS485-Project-People-Following-Robot
git switch person-world      # or main once things are merged
./scripts/build.sh

    If build.sh ends with a warning that TIAGo's model is not installed, run sudo apt install ros-jazzy-easynav-playground-tiago-worlds, or build it from source with ./scripts/fetch_tiago_source.sh.

  6. Pre-download the person model once 
    source /opt/ros/jazzy/setup.bash
gz fuel download -u "https://fuel.gazebosim.org/1.0/OpenRobotics/models/Standing person"
  7. Smoke test Run the quick start, then check the lidar works: 
    source scripts/env.sh
ros2 topic echo --once /scan --field ranges

    Mostly .inf with values around 2.5 for the person in front = good. Every value 0.16 = the GPU-lidar problem.

The WSL2 distro Ubuntu-ROS2 is already fully set up. What's different about it:

GPU via D3D12 fixed

Mesa 25.x on Ubuntu 24.04 falls back to llvmpipe on WSL. ~/.zshrc sets GALLIUM_DRIVER=d3d12 (only when /dev/dxg exists), which uses the NVIDIA GPU.

GPU lidar broken

Under D3D12 every lidar ray reads 0.16 m. The camera is fine. Use the lab machine for lidar work, or prefix GALLIUM_DRIVER=llvmpipe (correct, but about 10× slower).

sudo needs a terminal note

Run sudo commands in a real Ubuntu terminal, not through tools without a tty. Forgot the password? See troubleshooting.

How it works

Three layers talk to each other: Gazebo simulates the world and sensors, the ros_gz bridge translates between Gazebo and ROS messages, and ROS 2 nodes (TurtleBot 4 drivers, Nav2, our code, RViz) do the thinking.

What launch_sim.sh starts

  1. scripts/env.sh loads ROS and the workspace's install/, sets ROS_DOMAIN_ID=30, leaves discovery on the ROS default, and sets GZ_IP=127.0.0.1. Every script sources it.
  2. people_follower/launch/sim.launch.py sets GZ_SIM_RESOURCE_PATH so Gazebo finds our worlds and the TB4 models, then starts Gazebo with <world>.sdf -r (runs immediately) and a /clock bridge.
  3. Map lookup (find_map): if map:= isn't given, it looks for <world>.yaml in people_follower/maps, then in TurtleBot 4's maps. A missing map only matters with localization:=true.
  4. turtlebot4_gz_bringup/turtlebot4_spawn.launch.py spawns the robot on its dock at x, y, yaw and starts its bridges, the Create 3 and TB4 nodes, and, if requested, SLAM, localization, Nav2 and RViz.
i

The world's <world name=…> must match its file name. The TB4 bridges build topic names like /world/<world>/… from it.

The person model

Looks

The mesh comes from the Fuel model Standing person, rotated so the model's +x axis is the way the person faces. Starts at (2.5, 0), facing the robot.

Collides

A cylinder, 0.25 m radius and 1.8 m tall. Gazebo's DART physics can't collide with meshes. Gravity is off, so it never falls over.

Moves

VelocityControl takes a body-frame Twist on /model/human/cmd_vel. It keeps the last command until it gets a new one.

Reports

OdometryPublisher publishes its true world pose at 20 Hz on /model/human/odometry. That's useful as ground truth when testing the follower.

How the waypoint walker steers

!

Because Gazebo keeps the last velocity, both person scripts send a stop directly to Gazebo when they exit. Kill them some other way and the person keeps walking; see troubleshooting.

Waypoint planner

Click inside the arena to add waypoints for the person (drag to move, right-click to remove). The YAML on the right updates as you go. Paste it into src/people_follower/config/human_waypoints.yaml, then run ./scripts/build.sh.

Mapping & navigation

  1. Make a map Once per world: ./scripts/make_map.sh <world>. Undock, then drive the whole area with teleop while watching the map grow in RViz, turning slowly (press c a few times), then press Enter. If no new terminal opens for teleop, run ./scripts/launch_teleop.sh yourself.
  2. Commit the map src/people_follower/maps/<world>.yaml and .pgm, so the team has it.
  3. Navigate ./scripts/launch_nav.sh world:=<world> (this sets the starting pose for you), undock, then click "Nav2 Goal" in RViz, or run ./scripts/send_goal.sh 2 1.
  4. Automate ./scripts/nav_demo.sh world:=<world> -- -p goal_x:=3.0 -p goal_y:=-2.0 docks, localizes, undocks and drives.
!

Not yet verified end to end. The warehouse test on the WSL laptop was stopped during the first-time model download, and the WSL lidar issue blocks localization there anyway. Try it first on the lab machine.

Troubleshooting

Click a problem to expand it. The search box at the top filters these too.

build "Workspace not built yet" / "Package 'people_follower' not found"

The workspace has no install/ folder yet, or a new file hasn't been built.

./scripts/build.sh
./scripts/clean_build.sh      # if it still acts stale
build build.sh succeeds, but launch says a TurtleBot / Nav2 package is missing

build.sh runs rosdep install … || true: if rosdep needs sudo and can't get it, the failure is hidden. Install the packages yourself (see setup step 2) and check:

source /opt/ros/jazzy/setup.bash
rosdep check --from-paths src --ignore-src
sim No topics show up in another terminal

Every terminal must be on the same ROS_DOMAIN_ID (30 by default). Use the scripts, or:

source scripts/env.sh
ros2 topic list
sim The Gazebo window is black

Usually the first launch of a world that uses Fuel models (warehouse, depot): Gazebo downloads them before showing anything. Wait and watch the cache grow. Later launches are fast.

du -sh ~/.gz/fuel

If it stays black with no download, check the GPU (next item).

gpu Everything is slow / camera updates rarely

Probably software rendering (llvmpipe). Check:

glxinfo -B | grep "renderer string"
Lab machine

Install the GPU driver (sudo ubuntu-drivers install, reboot).

WSL laptop

echo $GALLIUM_DRIVER should print d3d12. A shell started before the ~/.zshrc change won't have it, so open a new one.

Measured on the WSL laptop with the TurtleBot 4 sim:

D3D12 (GPU)llvmpipe (CPU)
Real-time factor0.880.10
Camera rate~25 Hz~5 Hz
Gazebo window~70 FPS~12 FPS
gz server CPU~1.2 cores~4.4 cores
gpu Every /scan value is 0.16 WSL only

Gazebo's GPU lidar is broken under Mesa's D3D12 driver on WSL: every ray reads the minimum range. The camera renders fine. In software mode it's correct (the person at 2.5 m appears at about −90°). Walls don't change it.

GALLIUM_DRIVER=llvmpipe ./scripts/launch_sim.sh world:=person_world   # correct but slow

Expected to be fine on a native Linux GPU. Verify once on the lab machine with the smoke test in setup.

person The person keeps walking after I stopped the script

Gazebo's VelocityControl keeps the last command. The scripts send a stop when they exit, but not if they're killed hard. Stop the person directly:

source scripts/env.sh
gz topic -t /model/human/cmd_vel -m gz.msgs.Twist -p "linear: {x: 0}"
person The person doesn't move
  • Is the sim running world:=person_world? Other worlds have no person.
  • Teleop: its terminal must be focused while you press keys.
  • Are teleop and waypoints both running? They fight over the same topic. Run only one.
  • Waypoints stuck on "Waiting for /model/human/odometry": rebuild (./scripts/build.sh) so the updated world is installed.
cleanup The next launch misbehaves / old processes are still running

Closing windows instead of pressing Ctrl+C can leave dozens of nodes running, and a killed node can leave a locked file in /dev/shm that hangs later launches ("No clock received"). Check and clean up:

pgrep -af "gz sim|parameter_bridge|rviz2"
./scripts/kill_sim.sh
nav "No map found for this world"

person_world doesn't have a map yet. Make one with ./scripts/make_map.sh <world>, use warehouse/maze/depot, or pass map:=/path/to/map.yaml.

nav The robot doesn't move in Nav2 / RViz shows no map

AMCL needs to know where the robot is. Set "2D Pose Estimate" in RViz, or:

./scripts/set_initial_pose.sh 0 0 0

Make sure the node's initial_x/initial_y match where the robot spawned.

sim "Desired controller update period … faster than the gazebo simulation period"

Harmless. It appears with the stock TurtleBot 4 worlds too.

system Forgot the sudo password on WSL

From Windows PowerShell:

wsl -d Ubuntu-ROS2 -u root
passwd brevski
exit
system "sudo: a terminal is required to read the password"

The command ran somewhere without a real terminal (an editor or AI tool's shell). Run it in a normal Ubuntu terminal window.

Development workflow

Daily loop

git pull → git switch -c my-feature → build & test → commit → push → pull request into main.

When to rebuild

After adding files, worlds, maps, launch files or nodes. Edits to existing Python files apply immediately (symlink install).

Add a node

Put it in src/people_follower/people_follower/, add it to entry_points in setup.py, rebuild, then ros2 run people_follower <name>.

Add a world

Drop <name>.sdf into worlds/ with <world name='<name>'>, rebuild, then launch with world:=<name>. Copy the plugins from an existing world.
